Sitter

A spaced-repetition app for children. It runs in the browser and keeps progress on the device: no server, no login, no tracking. Public repository, MIT licence.

What it is

Three apps for a Norwegian fourth grader and the adults around them: a daily practice flow, a spoken two-player family game, and a parent-versus-child quiz. They share one scheduler file with no DOM dependency, so the logic that decides what to ask next is tested in Node without a browser.

Plain JavaScript, HTML and CSS. No framework, no build step, no dependencies. The files reviewed in a pull request are the files that ship.

Status is alpha, in use with real children and parents. A more advanced engine exists in private use and stays private.

The student app on a phone

Start here

core/retention-core.js is the scheduler. It decides when a card comes back, using a model of retrievability, stability and difficulty in the FSRS family with a 90 percent retention target. It keeps review logs, response time and prompt type, so the scheduler could later be swapped for a library without throwing away a child's history.

Then tests/retention-core.test.js. The tests state the intended behaviour, and they are what a change has to get past.

Tests and CI

110 tests in 8 files with Node's built-in test runner. CI runs on every pull request and every push to main, on Node 22, in three steps: a syntax check of every source file, the tests, and a validator that checks every question against the content schema.

The main branch is protected. Changes arrive by pull request, and the test job has to pass before a merge is allowed.

What it does not do

No sync. Progress lives in the browser's localStorage. Clearing site data deletes it. That is the price of zero tracking, and the first thing I would change for a paid product.

One grade. The content is validated for fourth grade only. The validator lives in scripts/ and runs in CI.

Reviewed, not certified. Questions follow the Norwegian curriculum and are marked for review where they have been tested with children.

No accounts, no analytics, no server. Nothing to scale and nothing to breach, which also means nothing is learned from usage.

Where the reasons are
  • docs/decisionsone file per decision, with the date and the reason
  • CHANGELOG.mdwhat changed, newest first
  • scripts/validate-sitter-content.mjswhat a question must satisfy
  • AGENTS.mdevery folder and root file, explained

How it is built

Much of the code is written with AI assistance. I decide what gets built and what merges. A change has to pass the syntax check, the 110 tests and the content validator before it can reach main, and the decision log says why it was made.

Two decisions so far: the app is static with no build step, so the reviewed files are the shipped files; and the source lives in folders while the three entry pages stay in the root, so the public URLs never move.
