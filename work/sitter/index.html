01

What it is

Three small apps for a Norwegian fourth grader and the adults around them: a daily practice flow, a spoken two-player family game, and a parent-versus-child quiz. All three load the same scheduler core, one JavaScript file with no DOM dependency, so the logic that decides what to ask next is tested in Node without a browser.

Plain JavaScript, HTML and CSS. No framework, no build step, no dependencies. The files reviewed in a pull request are the files that ship.

Status: alpha. In use with real children and parents. A more advanced engine exists in private use and stays private on purpose. This repository shows the product, not the platform.

03

Read this file first

core/retention-core.js is the scheduler. It decides when a card comes back, using a model of retrievability, stability and difficulty in the FSRS family, with a 90 percent retention target. It stores review logs, response time and prompt type, so the scheduler can later be swapped for a library like ts-fsrs without throwing away a child's history.

Then open tests/retention-core.test.js. The tests describe the intended behaviour more honestly than a diagram would, and they are what a change has to get past.

sitter.html            entry page, stays in the root so the URL stays
  app/sitter/          the student app: flow, mechanics, card packs
    core/retention-core.js   scheduler, mastery score, capture gate
      localStorage      one key per app, migration, backup
family-game.html       two-player game, same core

05

What it does not do

  • No sync. Progress lives in the browser's localStorage. Clearing site data deletes it. That is the price of zero tracking, and it is the first thing I would change for a paid product.
  • One grade. The content is validated for fourth grade only. The validator is in scripts/ and runs in CI.
  • Reviewed, not certified. Questions are based on the Norwegian curriculum and marked for review where they are tested with children.
  • No accounts, no analytics, no server. Nothing to scale and nothing to breach, which also means nothing is learned from usage.
Decisions

Static, no build step: the reviewed files are the shipped files. Source in folders, entry pages in the root, so the public URLs never move. MIT licence. Each decision is one file in docs/decisions, with the date and the reason.

AI and responsibility

The code is agent-assisted. That is the design, not a caveat. I decide what gets built, what is allowed to merge and what evidence a claim must carry. The tests, the CI gate and the decision log are how I keep that honest when the typing is fast.
